# Decision Log — tapLedger

This document records the core architectural and financial decisions governing tapLedger. Any future changes must be reflected here.

| ID | Title | Summary | Rationale & Rules |
|---|---|---|---|
| **D001** | Transaction allocations separated from transactions | Categories belong exclusively in `transaction_allocations`, not on `transactions`. | A single financial movement can split across multiple categories (e.g. ₹1,000 debit: ₹600 Food + ₹400 Household). Allocations sum must strictly equal transaction amount for categorized transactions. |
| **D002** | Pending affects account balances | `PENDING` transactions are included in real account balance calculations. | Pending means "unclassified in budget", not "money has not moved". If an expense left the bank, the account balance must immediately reflect it even before the user selects a category. Only `IGNORED` and `VOIDED` are excluded. |
| **D003** | Ignored reserved for non-transactions | The `IGNORED` status is strictly reserved for duplicate notifications, OTPs, promotions, or non-financial alerts. | Real transactions must never be marked ignored to hide them from the budget; proper kinds (Transfer, Fee, Refund, etc.) must be used instead. |
| **D004** | Category configuration snapshotted per budget month | `budget_allocations` stores a monthly snapshot of category metadata (`category_name_snapshot`, `bucket_snapshot`, etc.). | Changes to current category names or buckets must never rewrite or distort historical budget periods. |
| **D005** | Transfers represented as directed linked legs | Transfers are modeled via a `transfer_group_id` linking two separate transaction legs (`OUT` from source account, `IN` to destination account). | Accurately models asynchronous bank notifications (e.g., ATM withdrawal, credit card bill payment, inter-account transfer) without polluting expense budgets. |
| **D006** | Same-source notifications never auto-merged solely by amount/time | Two notifications from the same source with identical amount and timestamp are never blindly merged. | Users can legitimately make multiple identical payments (e.g. two ₹50 chai/metro payments minutes apart). Only Level 0 (identical deterministic fingerprint) or Level 1 (matching UPI ref) auto-dedupes. Cross-source candidates (GPay vs Bank SMS) use a ~10-minute matching proposal. |
| **D007** | Backup required before real data entry | Reliable backup and restore (via SQLite `VACUUM INTO` and SAF) must be verified before user inputs real financial data. | Financial data loss is unacceptable. Restore procedures must verify schema version, PRAGMA integrity, and application-level invariant checks. |
| **D008** | Active notification recovery enabled | When `NotificationListenerService` reconnects, it immediately queries `getActiveNotifications()` and replays through fingerprint/dedup pipeline. | Guarantees recovery from background OS kills or service restarts without creating duplicate records. |
| **D009** | Bank balance cross-check used as missed-event detection | Where bank notifications include "Avl Bal", tapLedger compares it with expected ledger balance. | Early detection of missed notifications, bank fees, or ledger discrepancies before month-end statement reconciliation. |
| **D010** | Closed months are immutable by default | Once a budget month is closed, it is locked. Modifying it requires explicit, audited reopening. | Historical financial integrity must be preserved. Any cross-month edits trigger automatic recalculation of both affected months. |
